# AI 메일 요청 검토 구현·검증 기록

작성일: 2026-11-17 (KST)

## 구현 결과와 연결 상태

1차의 인력계획서·개인 초대 등록에 **읽기 전용 메일 수집 → 인원별 분석 초안 → PMO 검토·승인 → 같은 인원/준비 작업 갱신**을 연결했다. 파란 좌측 메뉴·헤더, 흰 작업 영역과 캐릭터 디자인을 유지한다.

| 구분              | 현재 상태 | 검증 범위                                                                                                                 |
| ----------------- | --------- | ------------------------------------------------------------------------------------------------------------------------- |
| 가상 메일함       | 동작      | 실제 서버·SQLite·분석·검토·승인 경로를 사용해 검증                                                                        |
| 실제 메일 수신    | 미연결    | 기존 환경에 메일 제공자·인증 정보가 없었다. IMAP 읽기 전용 어댑터는 구현했으나 실제 회사 메일 로그인·수신은 검증하지 않음 |
| 실제 외부 AI 추론 | 미연결    | 기존 OpenAI 호환 설정을 재사용한다. API 키가 없어 실제 외부 모델을 호출하지 않음                                          |
| AI 호출 계약      | 검증      | 로컬 HTTP mock으로 실제 요청 형식, 구조화 응답·근거 검증, 오류 대체 경로 검증                                             |
| 기본 분석         | 규칙 기반 | 키 미설정·AI 실패를 명시하고 보수적으로 인원별 문장을 추출. 실제 AI 응답으로 표시하지 않음                                |

가상 메시지는 별도 결과를 하드코딩해 명단에 넣지 않는다. `server/mail/fixtures.js`의 제목·본문이 실제 수집·분석·초안 저장 API를 통과하며, PMO 승인 전에는 인원이나 준비 작업이 바뀌지 않는다.

## 실행과 빠른 시연

Node.js 22.13 이상이 필요하다. 검증 환경은 Node.js 24.22.1이다.

```bash
npm ci
cp .env.example .env
# .env에서 ADMIN_PASSWORD를 설정한다.
# 기본 MAIL_PROVIDER=mock, OPENAI_API_KEY는 비워도 된다.
npm run dev
```

`http://localhost:5173`에서 PMO로 로그인한다. 빌드 실행은 `npm run build` 다음 `npm start`, 기본 접속 주소는 `http://localhost:3001`이다.

1. **인원 명단 → 인력계획서 불러오기**에서 프로젝트 SFA를 선택하고 [메일검토_기준인력.xlsx](../public/examples/메일검토_기준인력.xlsx)를 올린다. 회사는 샘플테크, 이름은 김민수, 생년월일은 1990-01-01이다. 파일 링크는 메일 검토 화면에도 있다.
2. 매핑과 행을 확인한 뒤 확정하고 김민수의 개인 초대 링크를 발급한다.
3. 다른 브라우저에서 링크를 열어 연락처와 투입일 **2026-11-23**, 종료일 **2027-06-30**을 입력해 본인 등록을 완료한다. 필요하면 기존 교육·서류를 먼저 완료해 보존 동작을 확인한다.
4. PMO의 **AI 메일 요청 검토 → 받은편지함**에서 기본 폴더 `PMO/인력요청`으로 **새 메일 확인**을 누른다.
5. **수행사 투입 요청 2건** 팝업이 나타난다. 닫아도 검토함에서 다시 열 수 있다. 목록에는 5통이 먼저 보이고 관련 요청 2통에서 초안 2건이 생긴다. 회의·현황 공유 회의·식당 안내는 초안 0건이다.
6. 김민수 초안에서 김민수의 고유 기록을 선택한다. 기존 11월 23일 → 제안 **11월 25일**, 원문 근거와 마감일 변경 예상을 확인한 뒤 검토 확인·승인한다.
7. 이서연 초안에서 **11월 23일 신규 투입**, **개발망 계정 신청**을 확인한다. 신규 기록 생성 확인 후 승인한다. 반영 완료 카드에서 바로 초대 링크를 생성한다.
8. 김민수는 같은 UUID와 본인 등록 상태를 유지한다. 이서연만 본인 등록 대기가 되고, 개발망 계정 작업의 대상도 이서연 한 명이다.
9. 같은 폴더에서 다시 확인하면 새 초안은 0건이다.
10. 상단 **설정**에서 폴더를 `PMO/날짜미정검증`으로 바꾸어 범위를 저장한다. ‘다음 주 예정, 날짜 미정’은 빈 투입일과 확인 필요로 표시되며 날짜 미확정 승인은 차단된다. 검토 메모를 남기고 **검토 보류**할 수 있다. 조건부 요청은 별도 조건 충족 확인도 필요하다.
11. **설정**에서 폴더 `PMO/회신검증`을 확인한다. 김민수의 최신 보류 요청만 새 초안이 되고, 인용된 이서연 요청은 다시 추출하지 않는다. 이전 요청·반영 이력을 같이 볼 수 있다.

검토 중 다른 창에서 대상 인원의 투입일을 바꾸면 승인이 409로 차단된다. 화면을 최신값으로 갱신하고 **최신 값 확인 · 다시 검토**한 다음 다시 검토 확인을 해야 승인할 수 있다.

## 실제 메일 연결에 필요한 설정

현재 제공자는 확인되지 않았으므로 Gmail/Outlook/Dooray의 계정이나 API 주소를 가정해 연결하지 않았다. 회사에서 **IMAP 접근을 지원한다고 확인한 경우** 다음 설정으로 준비된 어댑터를 사용할 수 있다.

```dotenv
MAIL_PROVIDER=imap
MAIL_IMAP_HOST=회사가-확인한-IMAP-호스트
MAIL_IMAP_PORT=993
MAIL_IMAP_USER=수집용-계정
MAIL_IMAP_PASSWORD=제공자가-허용한-비밀번호-또는-앱비밀번호
# 비밀번호 대신 제공자의 유효한 OAuth access token을 사용할 수도 있다.
MAIL_IMAP_ACCESS_TOKEN=
MAIL_FOLDER=INBOX
MAIL_SEARCH=인력
MAIL_SINCE=2026-11-01
```

필요한 항목은 다음과 같다.

- 실제 제공자, TLS IMAP 호스트·포트, 수집용 계정과 읽기 권한, 정확한 폴더/라벨 경로.
- 제공자가 허용한 앱 비밀번호 또는 IMAP 읽기 범위가 있는 OAuth 토큰. OAuth 발급·자동 갱신은 제공자별 운영 설정이 필요하다. 서버에 만료된 access token만 두면 다시 인증해야 한다.
- 실행 환경에서 해당 IMAP 호스트의 TLS 포트(보통 993)와 AI API 호스트의 HTTPS 443 접근 허용. 현재 클라우드 환경은 패키지 저장소 중심의 네트워크 허용 정책이므로, 실제 서비스 호스트는 운영 설정에서 확인해야 한다.
- 서버 재시작 후 PMO 화면에서 폴더·검색어·수신 시작일 확인. 이미 UI에서 저장한 범위가 있으면 환경변수 기본값보다 우선하므로 실제 폴더로 바꿔 **범위 저장**한다.

IMAP은 `readOnly: true`로 열어 **EXAMINE**을 사용하고, 본문 조회는 라이브러리의 **BODY.PEEK** 경로를 사용한다. 읽음 표시 변경, 이동, 삭제, 회신·발송은 호출하지 않는다. TLS 검증을 끄는 옵션도 제공하지 않는다. 최근 UID 50통을 처리하며 원문 크기 1MiB 초과는 건너뛴다. 분석용 본문은 최대 100,000자로 제한하고 첨부 내용은 분석하지 않는다. 수신 시작일은 KST 자정 기준이다.

IMAP을 지원하지 않고 Graph/Gmail API 등만 허용하는 제공자라면 해당 제공자의 읽기 전용 수집 어댑터가 추가로 필요하다. 현재 이를 실제 연결 완료로 간주하지 않는다.

## 실제 AI 연결에 필요한 설정

1차의 다음 서버 환경변수를 그대로 재사용한다.

```dotenv
OPENAI_API_KEY=사용할-API-키
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-4.1-mini
```

호환 서비스는 `/chat/completions`와 JSON 응답을 지원해야 한다. 서버가 제목·수신일·최신 본문을 분석 데이터로 전송한다. 이전 인용문과 전체 인원 DB는 전송하지 않는다. 메일 분석에는 이름·회사 등 실제 요청 이해에 필요한 본문이 포함되므로 운영 시 해당 AI 제공자 사용 범위를 확인해야 한다.

메일 본문의 지시문은 시스템 명령이나 실행 도구로 취급하지 않는다. 모델에는 상태 변경 도구를 제공하지 않으며, JSON만 받아 Ajv 스키마와 원문 근거를 검증한다. 추론 출력은 항상 검토 초안이다. AI 키가 없으면 `AI 미연결`, 호출·출력 검증 실패는 `규칙 기반 대체`를 표시한다. 이미 처리한 메시지를 다시 동기화해도 재분석·중복 초안을 만들지 않는다. 새 연결 검증은 새로운 메시지로 진행한다.

## 분석 데이터와 검토 규칙

응답은 `requests[]`이며 한 요청에 다음 정보를 둔다.

| 값                                   | 내용                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| type                                 | new / change / hold                                                                 |
| project, company, name               | 대상 프로젝트·수행사·인원명, 불명확하면 null                                        |
| startDateRequested, endDateRequested | 날짜 변경 요청 여부                                                                 |
| startDate, endDate                   | 확정 가능한 ISO 날짜 또는 null                                                      |
| tasks                                | account/access/education/document 분류, 작업명, request/hold/cancel 처리, 원문 근거 |
| evidence                             | 유형·대상·날짜별 정확한 원문 구절                                                   |
| clarifications, conditional          | 확인 필요 목록과 조건부 요청 여부                                                   |
| resume                               | 명시적인 기존 보류 해제 여부                                                        |

근거가 원문에 없으면 값을 비우거나 해당 요청을 제외한다. 연도 생략 시 해당 프로젝트 기존 인원의 투입 연도가 하나로 일치할 때만 기준 연도로 사용하고 확인 사항에 근거를 표시한다. 기준 연도나 여러 날짜 중 어느 날짜인지 불명확하면 값을 비워 PMO가 확인한다. 다른 인원의 근거가 섞인 작업은 제외하고 확인 사항으로 남긴다. 지원하는 인력 요청이 없는 메일은 초안 0건이다. 규칙 대체 분석은 `프로젝트:`, `수행사:`와 `인원명: 요청`, `[프로젝트]` 제목과 `소속회사 인원명 님의/님이 요청` 형태를 지원하며 일반적인 자유 형식 전체를 이해하는 AI를 대신한다고 표시하지 않는다.

PMO는 대상 UUID를 직접 선택하고 원문·기존값·제안값을 확인한다. 동명이인은 여러 후보를 보여주며 자동 병합하지 않는다. 신규는 별도 신규 기록 생성 확인이 필요하다. 유형·대상·날짜·작업 등 추출값을 바꾸면 검토 메모로 수정 근거를 남긴다. 검토 보류는 초안 상태만 바꾸며 인원을 투입 보류로 만들지 않는다. 반대로 **투입 보류 유형의 승인**은 선택한 인원의 투입 준비를 보류한다.

## 인원·작업 반영 규칙

- `server/personnel.js`의 공통 신규 등록 함수를 인력계획서·수동 등록·메일 승인에서 재사용한다. 신규 UUID를 만들고 본인 등록 대기로 저장하며, 이후 1차 초대 API를 사용한다.
- 기존 인원은 선택한 UUID를 갱신한다. 등록 상태·완료 교육·제출 서류와 파일·제출 버전을 유지한다. 완료한 작업의 마감일도 보존한다.
- 1차에는 인원별 준비 마감일 규칙이 없어 `src/personnel-workflow.js`에 공통 규칙을 추가했다. 수동 투입일 수정, 개인 등록과 메일 승인에 같은 함수를 사용한다.
- 기본값: eGIS/Dooray 신청 D-3, 발급·최초 접속·교육·서류·출입 D-1, 최종 준비 확인 D0. 주말·공휴일을 제외하지 않는 달력일 기준이다. `settings.preparationDeadlineRules[프로젝트][taskId]`의 -60~0일 설정이 있으면 기본 작업에 우선 적용한다.
- 추가 작업에 별도 기한이 있으면 기존 투입일과 기한의 간격을 유지한다. 메일에서 새로 만든 개발망 계정 작업은 D-3이다. 개인별 기한은 `person.taskOverrides`에 저장하므로 공통 템플릿이나 다른 인원의 기한을 바꾸지 않는다.
- 요청한 eGIS/Dooray·출입·기본 교육/서류는 기존 작업을 재사용한다. 개발망 등 별도 항목은 대상 UUID 한 명만 가진 추가 작업으로 만든다. 기존 교육·서류 양식 외의 임의 항목은 일반 확인 작업이며 별도 LMS·전자서명·임의 서류 업로드 양식을 자동 생성하지 않는다.
- 계정·출입 요청은 준비 작업에 기록하며 외부 계정 발급/회수 API를 실행하지 않는다. 완료 상태는 보류·취소 요청으로도 자동 초기화하지 않는다.
- 투입 보류는 `onboardingHold`와 투입 상태에 기록하고 미완료 작업의 실행을 보류한다. 본인 등록·이미 완료한 교육/서류를 초기화하지 않는다. 보류 해제는 PMO가 해당 요청으로 확인한 경우에만 반영한다.
- 기간 변경 시 아직 제출하지 않은 온라인 서류 초안은 화면에서 최신 기간으로 갱신하고 다시 확인·서명하도록 한다. 이미 제출한 원본과 완료 상태는 그대로 둔다. 기간 변경에 따른 완료 서류 재징구는 자동 처리하지 않는다.

## 저장·중복·동시 검토

기존 SQLite DB에 `mail_settings`, `mail_messages`, `mail_requests`, `mail_request_history`를 추가했다. 메일 원문 텍스트·인용문, 분석 방식, 스키마 검증한 초안, PMO 수정본·검토 상태, 대상 인원 스냅샷·기록 버전과 반영 결과를 보관한다. 비밀값은 저장하지 않고 서버 환경변수에서 읽는다.

- 수집 고유키: **메일 계정 ID + 메시지 ID**. 검색어나 폴더를 바꾸어도 계정 ID는 유지한다. Message-ID가 없는 IMAP 메시지는 폴더·UIDVALIDITY·UID 조합을 사용한다.
- 최신 회신은 별도 메시지로 저장하고 References/In-Reply-To로 대화를 연결한다. 최신 본문과 `Original Message`/`>`/회신 헤더 인용문을 분리한다. 프로젝트·회사·이름이 같은 최신 회신이 오면 이전 미승인 초안을 대체 처리하고 이력으로 남긴다. 이미 반영한 요청은 지우지 않으며 후속 초안과 함께 보여준다.
- 초안 버전과 대상 `recordVersion`을 검증한다. 검토 중 인원이 달라졌으면 409로 차단하고 최신값 확인·재검토를 요구한다.
- 승인에는 하나의 SQLite 트랜잭션을 사용한다. 인원·작업 저장과 요청의 반영 완료 처리가 함께 성공해야 완료된다. 이미 반영한 요청 재시도는 저장된 인원 ID와 결과를 반환한다.
- PMO 전용 API다. 프로젝트 담당자와 수행사는 메일 원문·초안 조회 및 동기화·승인을 할 수 없다. 팝업 닫기 기록은 세션 저장소에 요청 ID만 보관하고, 초안과 반영 상태의 원장은 서버에 둔다.

## 주요 API

| API                                 | 동작                                  |
| ----------------------------------- | ------------------------------------- |
| GET /api/mail/inbox                 | 연결 모드·수집 범위·초안·메일 목록    |
| PUT /api/mail/settings              | 폴더·본문 검색어·수신 시작일 저장     |
| POST /api/mail/sync                 | 읽기 전용 수집·중복 제거·분석·새 초안 |
| GET /api/mail/messages/:id          | 최신 본문·인용문·분석 출처            |
| POST /api/mail/messages/:id/analyze | 처리 오류인 메시지 다시 분석          |
| GET /api/mail/requests/:id          | 기존값·후보·원문·이전 요청·수정 이력  |
| PATCH /api/mail/requests/:id        | 초안 수정, 인원에는 미반영            |
| POST /api/mail/requests/:id/hold    | 검토 보류                             |
| POST /api/mail/requests/:id/rebase  | 최신 인원 버전을 확인한 재검토        |
| POST /api/mail/requests/:id/approve | 검토한 초안의 트랜잭션 반영           |

## 검증과 한계

최종 검증: 서버·로직 테스트 **41개**, 브라우저 시나리오 **8개** 통과, 프로덕션 빌드 성공. 테스트는 실제 개인정보가 아닌 예제 인원을 사용한다.

- 1차 XLSX → 김민수 본인 등록 → 메일 초안 두 건 → 김민수 23일에서 25일로 같은 ID 갱신 → 이서연 23일 신규 대기·개발망 작업·초대 발급.
- 기존 교육·서류 상태, 원본과 제출 버전 보존, 완료 작업 기한 유지, 다른 인원·공통 작업 기한 불변.
- 날짜 미정·조건부 요청, 초안 수정·보류, 일반 메일 초안 0건.
- 동일 메일 재수집, 동명이인 선택, 초안/인원 충돌과 재검토, 승인 중복·재시도.
- 반영 완료 표시 실패를 강제로 일으켜 인원·작업도 함께 롤백되는지 검증.
- 최신 회신의 인용문 제외, 이전 미승인 요청 대체, 이전 반영 이력 조회.
- PMO 전용 권한, 비밀값 비노출, 실제 MIME 파서의 단일 References 처리와 KST 날짜 경계.
- 로컬 AI mock 응답의 스키마·근거·인원별 작업 귀속과 호출 실패 대체.
- 실제 브라우저의 팝업 닫기/재조회, 기존값 변경 감지 후 재승인, 링크 발급, 미제출 서류 기간 갱신.

실행 명령은 `npm test`, `npm run test:browser`, `npm run build`다. 브라우저 테스트는 1차와 메일 검토를 서로 다른 임시 DB·포트(5180/3011, 5181/3012)로 분리하며 사용자 DB를 초기화하지 않는다. 실제 IMAP 로그인·메일 수신, 실제 외부 AI 결과 품질·회사 OAuth 정책은 연결 정보가 마련된 환경에서 추가 검증해야 한다.
