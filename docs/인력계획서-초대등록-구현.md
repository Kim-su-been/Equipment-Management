# 인력계획서 불러오기·개인 초대 등록 구현 기록

검증일: 2026-11-17 (KST)

## 기존 구조와 변경

기존 서비스는 React 19/Vite 7/ExcelJS 기반 SPA였다. 프로젝트는 SFA/그룹웨어 문자열, 인원은 SFA-1/GW-1 같은 표시 ID였고 명단·작업·설정은 localStorage, 제출 원본은 IndexedDB에 저장했다. 계정·교육·온라인 서류·검토·프로젝트별 추가 작업·작업 양식 내보내기 UI를 재사용했다.

Node HTTP 서버와 Node 내장 SQLite를 추가했다. 프런트엔드 상태를 변경 전 값이 포함된 패치로 저장하며, 서버가 세션/프로젝트/개인 범위와 동시 수정 충돌을 검증한다. 서로 다른 작업에서 이력을 동시에 추가하면 두 이력을 모두 보존하고, 실제 업무 필드의 충돌은 차단한다. UI는 2초마다 변경 리비전을 확인하고 창 활성화·새로고침 시에도 서버 상태를 조회한다. 업로드 엑셀과 제출 원본은 DB BLOB으로 보관한다. 브라우저를 바꾸어도 동일한 상태·원본을 조회한다.

서버가 새 참여 건마다 UUID를 만들고, 표시 코드는 별도로 유지한다. 본인 등록은 신규 인원을 생성하지 않고 초대에 연결된 UUID를 갱신한다. 프로젝트마다 별도 참여 기록을 두므로 다른 프로젝트의 동명이인을 합치지 않는다.

SQLite는 WAL/외래키/트랜잭션을 사용한다. 서버 재실행 후 DB와 초대 암호키를 재사용한다. 기본 경로는 `data/readyboard.sqlite`, 자동 생성 키는 같은 폴더의 `invitation.key`다. 환경변수로 고정 키를 지정할 수도 있다. 실행 중 백업은 SQLite backup API를 사용하거나 서버를 종료한 상태에서 수행한다.

## 엑셀과 AI 매핑

ExcelJS가 원본을 읽고 AI 또는 규칙이 `{sheet, headerRow, columns:{company,name,birth}}`를 제안한다. 시트 인덱스는 0부터, 행·열은 1부터다. AI에는 인식 가능한 헤더/구조 키워드, 행/열 위치, 병합 범위, 마스킹 샘플만 보낸다. 이름·회사명·실제 생년월일은 보내지 않는다. AI 응답은 시트·행 존재 여부와 서로 다른 열 범위를 서버에서 다시 검증한다.

- 키 없음: **AI 미연결 · 열 이름 기반 후보**.
- 호출 실패 또는 잘못된 매핑: **수동 지정 안내**.
- confidence < 0.8: **불확실하므로 직접 확인 안내**.
- 모든 경우: PMO의 시트·헤더·열 확인과 원본 기반 미리보기 필수.

시트 수 20개, 시트당 2,000행·100열, 파일 10MB와 선언된 압축 해제 총량 50MB 제한을 적용한다. 원본 시트는 처음 35행을 구조 확인용으로 제공하며, 확정 시 선택한 매핑에 따라 전체 허용 행을 원본에서 다시 읽는다. 날짜 객체·일반 ISO/숫자 날짜·Excel 일련번호·1904 날짜 체계와 생년 단독 값을 구분한다. 생년만 있거나 비어 있으면 월·일을 만들지 않고 본인 확인 대상으로 남긴다.

미리보기는 원본 시트·행, 추출값과 검토 상태를 표시한다. 수정과 제외를 지원한다. 같은 프로젝트의 이름 후보는 표시만 하며 자동 병합하지 않는다. PMO가 기존 인원 연결을 선택하면 원래 인적 사항은 유지하고 새 파일 출처를 추가한다. 신규 등록은 동명이인도 별도 UUID를 만든다.

확정은 하나의 트랜잭션이다. 오류가 있으면 해당 확정 요청 전체를 저장하지 않는다. 확정한 원본 행의 고유키는 재업로드·재시도 시 기존 person ID를 재사용한다. 같은 바이트의 파일은 이름을 바꾸어도 파일 해시가 같아 같은 업로드로 인식한다. 내용이 바뀐 파일은 새 업로드이므로 이름 후보와 대조하고 PMO가 연결 여부를 결정한다.

## 주요 API

| API                                 | 대상 / 동작                                        |
| ----------------------------------- | -------------------------------------------------- |
| GET /api/session                    | 로그인 상태·허용 범위 초기 조회                    |
| POST /api/admin/login               | PMO 또는 프로젝트 담당자 비밀번호 세션             |
| POST /api/logout                    | 세션 종료                                          |
| GET /api/state                      | 세션 범위에 맞춘 명단·상태                         |
| PATCH /api/state                    | 필드별 변경 전 값 대조, 권한 확인 후 갱신          |
| POST /api/imports?project=…         | PMO 전용 raw XLSX 업로드·매핑 제안                 |
| POST /api/imports/:id/preview       | 확정 매핑으로 원본 추출·기존 후보 조회             |
| POST /api/imports/:id/commit        | 선택/검토한 행만 확정, 재시도 결과 재사용          |
| POST /api/people                    | 기존 수동 등록 경로, stable UUID와 요청 ID 재사용  |
| GET/POST /api/people/:id/invitation | PMO 전용 링크 조회·생성·재발급                     |
| GET /api/invites/:token             | 개인 링크 유효성·한 명의 기본 정보                 |
| POST /api/invites/:token            | 기본 정보 일치·추가 정보 확인, 같은 기록 등록 완료 |
| POST /api/files?personId=…&taskId=… | 세션 범위와 소유 인원을 확인해 원본 저장           |
| GET /api/files/:id                  | 소유 인원 접근 권한 확인 후 원본 조회              |
| POST /api/migrate                   | PMO의 이전 브라우저 명단 이전                      |
| GET /api/health                     | 서버/SQLite 경로 상태                              |

상태 코드: 미로그인 401, 범위 위반 403/404, 만료·재발급·사용한 초대 410, 동시 수정 충돌 409, 입력/매핑 오류 400.

초대는 난수 32바이트 토큰을 사용한다. DB에는 검색용 SHA-256과 PMO 재조회용 AES-256-GCM 암호문을 저장하며 로그에는 토큰을 기록하지 않는다. 세션도 해시를 저장하고 HttpOnly/SameSite 쿠키를 사용한다. 재발급은 앞선 미사용 초대를 종료하고, 등록 완료는 같은 인원에 남아 있는 초대를 사용 완료 처리한다. 반복 제출은 410이며 인원이 추가되지 않는다.

링크 등록은 링크 소유와 기본 정보 확인 방식이다. 주민등록 등 외부 신원 확인을 뜻하지 않는다. 개인 등록 후 해당 브라우저의 세션은 24시간 유지된다. 세션이 끝나고 링크도 이미 사용됐다면 PMO 문의가 필요하며 별도의 운영용 직원 재로그인/계정 복구는 후속 범위다.

## 이전 데이터와 좌석 제거

이전 localStorage가 있는 브라우저에서 PMO의 운영 기준에 가져오기 버튼이 표시된다. 기존 프로젝트/ID에서 결정적으로 UUID를 만들므로 반복 이전이 인원을 늘리지 않는다. IndexedDB에 접근 가능한 최신 제출 원본도 업로드하고 파일·제출 버전의 연결을 수정한다. 기존 원본을 찾을 수 없으면 재제출 필요 메시지를 표시한다. 기존 데이터 자체는 브라우저에서 삭제하지 않는다.

좌석 화면·배정·드래그·버전 UI와 seed 좌석 데이터, 작업 O14/O15 및 연관 안내 O07을 제거했다. 이전 좌석·버전은 SQLite 아카이브로 보존한다. 준비율은 계정·출입/교육/서류 분류의 필수 작업을 사용하고 최종 충족 판정도 같은 기준을 사용한다. 기타 추가 작업은 준비율에서 제외한다.

## 테스트와 결과

`npm test` 27개, `npm run test:browser` 4개 시나리오가 모두 통과했다. `npm run build`도 성공했다. 테스트는 실제 개인정보가 아닌 예제 인원을 사용한다.

- A: `소속회사 / 이름 / 생년월일` 정상 추출·ISO 저장.
- B: 제목·빈 행 뒤 `업체명 / 투입인력 / 생년` 헤더 탐색, 월·일 null과 확인 필요 표시, 같은 이름 두 명의 별도 UUID.
- 원본 시트·행과 수정 전 출처 보존, 비표준 다중 시트 수동 매핑·값 수정·행 제외.
- 파일 재업로드·확정 재시도·수동 등록 요청 재시도에서 기록 수와 UUID 유지.
- 동일 이름 기존 후보 표시, 선택 누락 차단, 명시적 기존 연결 시 인적 사항 보존.
- 별도 Chromium 컨텍스트에서 본인 등록 후 PMO 새로고침 → 동일 UUID 등록 완료 확인.
- 링크 만료·재발급으로 이전 링크 종료·사용 링크 재접속·반복 제출 차단.
- 생년 단독 인원의 월·일 추가, 원래 생년/생년월일과 다른 입력 차단.
- 서류 작성·제출 및 교육 수료증의 서버 보관, PMO 세션에서 같은 원본 다운로드.
- 프로젝트 담당자 범위/PMO 전용 업로드·초대 API 제한, 미로그인 차단, 변경 충돌 검출.
- AI mock 호출에서 실제 이름·회사·생년월일 미전송 및 잘못된/실패한 제안 대체 경로 검증. 실제 외부 LLM은 키가 없어 호출하지 않았으며 UI에서는 AI 미연결을 표시했다.
- 서버를 종료·다시 생성한 후 UUID·대기 상태·세션·현재 초대와 암호문 재조회 유지.
- 이전 데이터의 결정적 UUID 이전, 좌석/버전 제거와 기존 준비율, 온라인 문서·작업 권한·ZIP·PDF 해시 회귀 검증.

최종 실행 결과는 작업 완료 시 실행한 `npm test`, `npm run test:browser`, `npm run build`를 기준으로 한다. 실행 방법과 환경변수는 [README](../README.md)에 정리했다. 브라우저 테스트는 임시 DB와 별도 포트를 사용하므로 사용자 데이터를 초기화하지 않는다.

## 향후 메일 변경 요청 연결

메일 수신/AI 해석/자동 반영은 이번에 구현하지 않았다. 후속 모듈은 이름이 아닌 person UUID를 확정하고 `recordVersion`, 출처 메일 ID, 변경 전후 값, PMO 승인 결과를 포함한 명령으로 갱신해야 한다. 현재 필드별 변경 전 값 검증과 감사 이력 경로를 재사용할 수 있다. 내용이 달라진 인력계획서는 동일 인원을 자동 덮어쓰지 않고 PMO의 기존 인원 연결을 요구한다.
