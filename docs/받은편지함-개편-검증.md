# 받은편지함 개편 및 시연 검증

## 화면과 처리 흐름

기존 ‘AI 메일 요청 검토’ 메뉴는 받은편지함부터 연다. 넓은 화면에서는 왼쪽에 발신자·제목·본문 미리보기·수신 시각, 오른쪽에 전체 본문이 보인다. 작은 화면은 위아래로 배치한다. 기존 푸른색 헤더·사이드바와 캐릭터 디자인을 유지했다.

- 폴더/라벨, 검색어, 수신 시작일은 상단 **설정**에서 저장한다. 수집 연결 범위이며 인력 요청 관련성 분류와 별개다.
- **새 메일 확인**은 먼저 모든 메일을 저장하고 목록에 표시한다. 브라우저가 목록을 그린 뒤 두 번째 API 요청에서 실제 분석을 시작하며 **새 메일 분석 중**을 표시한다.
- 시연 기본 폴더의 메일은 일정 변경, 신규 투입, 정기회의, 투입 현황 공유 회의, 식당 안내 총 5통이다. 변경·신규 두 메일만 초안을 만들고 일반 3통도 본문을 읽을 수 있다.
- 완료 후 새로 생성된 초안과 관련 메일의 수에서 팝업 숫자를 계산한다. ‘수행사 투입 요청 2건 / 새 메일 5통 중 수행사 투입 관련 메일 2통을 찾았습니다.’ 팝업을 한 번 표시한다.
- 팝업의 **검토하기**는 이번 초안을, **검토 대기 N건**은 누적 검토함을 연다. 메일별 **AI 검토 열기**로도 해당 요청을 확인할 수 있다. 팝업을 닫거나 페이지를 새로고침해도 서버에 저장한 초안은 남는다.

## 재사용과 저장

`server/mail/service.js`의 초안 저장·후보 선택·버전 충돌·재검토·승인 트랜잭션을 재사용한다. `src/MailReviewPage.jsx`의 원본 메일, 원문 근거, 기존값과 제안값, 마감일 미리보기, 보류·승인·초대 발급 화면을 유지했다.

`src/personnel-records.js`의 대기 인원 생성과 `src/mail-application.js`의 개인별 작업 변경 함수를 서버와 독립 HTML이 공유한다. 서버의 권한·검토 확인·중복 승인 검사·SQLite 트랜잭션은 계속 서버에서 검증한다. UUID·등록 상태·기존 초대·완료 교육/서류는 유지하고 미완료 작업의 개인별 기한만 갱신한다.

`POST /api/mail/sync`는 기존 본문 `{}` 호출을 지원한다. UI는 `{collectOnly:true}`로 모든 메일을 먼저 SQLite에 저장하고 반환된 `analysisIds`를 `{analyzeIds:[...]}`로 분석한다. 처리된 메일은 재분석하지 않고 메일함+메시지 고유키와 승인 기록으로 중복을 막는다. 분석 중 탭을 닫아도 원문은 남으며 다음 **새 메일 확인**으로 미처리 분석을 재시도한다. 별도 백그라운드 스케줄러는 없다.

## 실제 AI와 시연 구분

현재 환경은 실제 메일 인증 정보와 AI API 키 없이 검증했다. 가상 메일도 서버의 동일한 분석·검토·승인 경로를 사용한다. AI 키가 설정되면 기존 OpenAI 호환 모델을 모든 수집 메일에 호출하고, 없거나 호출/스키마 검증에 실패하면 각각 **AI 미연결 / 규칙 기반 대체**를 명시한다. 실제 외부 모델의 응답 품질과 실제 회사 메일 수신은 이번에 검증하지 않았다. 로컬 AI 응답 서버로 모델 요청·스키마 검증·실패 대체를 시험했다.

규칙 분석은 제목과 최신 본문에서 인원명·소속·실제 신규/변경/보류 요청을 추출한다. 메일 ID·순서·기대 결과는 분류 입력으로 사용하지 않는다. 이름과 명시적인 요청이 없는 ‘수행사 투입 현황 공유 회의’는 0건이다. 월·일만 있을 때 프로젝트 기존 투입 일정의 연도가 하나로 일치하면 해당 연도를 사용하고 확인 사항에 표시한다. 연도 근거가 없거나 충돌하면 날짜를 비워 확인을 요구한다.

실제 회사 연결은 기존 `.env.example`의 `MAIL_PROVIDER=imap`, `MAIL_IMAP_HOST/PORT/USER`, 비밀번호 또는 액세스 토큰과 `MAIL_FOLDER/SEARCH/SINCE`를 사용한다. 실제 AI는 `OPENAI_API_KEY`, `AI_BASE_URL`, `AI_MODEL`을 서버에 설정한다. 연결 방식과 한계는 [기존 구현 문서](AI-메일요청-검토-구현.md)를 참고한다.

## 실행 및 시연

Node.js 22.13 이상에서 다음 순서로 실행한다.

```bash
npm ci
cp .env.example .env
# .env에 ADMIN_PASSWORD를 설정. 기본 MAIL_PROVIDER=mock.
npm run dev
```

`http://localhost:5173`에서 PMO로 로그인한다. SFA 프로젝트에 예제 `public/examples/메일검토_기준인력.xlsx`를 등록하고 초대 링크에서 김민수의 투입일을 2026-11-23으로 입력한다. **AI 메일 요청 검토 → 새 메일 확인**을 누른다. 다른 명단을 사용하는 경우 시연 메일은 실제 기존 인원의 프로젝트·이름·소속을 사용한다. 신규 이름은 기존 명단과 겹치지 않게 선택한다.

팝업을 닫아 검토 대기 2건을 확인한다. 일반 메일을 읽은 뒤 김민수 초안만 승인하면 기존 ID로 25일이 되고 이서연은 아직 생성되지 않는다. 이서연도 검토·승인하면 ‘본인 등록 대기’로 생성되며 개발망 계정 작업은 이서연에게만 배정된다. 초대 링크는 기존 화면에서 발급한다.

## HTML 확인

```bash
npm run export:review
node tests/review-html.mjs
```

`preview/readyboard-review.html`과 ZIP에 자산과 합성 데이터를 포함한다. 상단 **받은편지함 열기 → 새 메일 확인**부터 승인·명단 반영을 시연할 수 있다. 분석·작업 변경은 실제 서비스의 공통 함수를 실행한다. HTML은 브라우저 탭 메모리만 사용하므로 새로고침하면 초기화되며 실제 DB·회사 메일·AI와 연결되지 않는다. 실제 파일 저장·개인 초대 접속은 서버 실행이 필요하다. HTML의 초대 링크는 표시용이다. Windows에서 파일 열기가 제한되면 ZIP을 풀어 `open-preview.cmd`를 실행한다(Node.js 필요).

## 검증 결과

- `npm test`: 서버·로직 테스트 41개 통과. 수집 직후 5통·초안 0건, 이후 초안 2건, 역순/ID 없이 본문 분류, 중복 수집·승인, 동명이인, 미정 날짜, 회신 이력, 충돌·롤백을 확인했다.
- `npm run test:browser`: Chromium 시나리오 8개 통과. 분석 요청을 대기시킨 상태에서 먼저 5통이 목록에 보이는 것을 확인하고, 분석 후 초안 2건과 팝업 1회를 확인했다. 팝업을 닫아도 검토 대기가 유지되고 일반 메일 본문도 읽힌다. 김민수만 승인하면 같은 ID로 25일이 되고 이서연은 아직 생성되지 않는다. 별도 수행사 브라우저에서 변경된 일정과 서류 작성 기간도 확인했다.
- `node tests/review-html.mjs`: 내보낸 HTML을 로컬 HTTP로 열어 5통/2건, 일반 메일 제외, 한 건 승인, 신규 승인, 재확인 초안 0건, 데스크톱·390px 모바일과 브라우저 오류 없음을 확인했다.
- `npm run build`: 프로덕션 빌드 성공. 기존 ExcelJS 청크 크기 안내가 남아 있다.

검증은 임시 DB와 합성 자료를 사용하며 사용자 DB를 초기화하지 않는다. 원격 `master`는 변경하지 않고 미리보기 브랜치에만 구현 소스와 HTML을 함께 반영한다.
